# NodeGraph

Node graphs that **generate source code**. A graph is edited in NimbleEditor
and compiled on save; the generated code is **stored in the graph file
itself**, at its end (`<gen_code>`), and nothing is written beside it. That
stored code is what a game's cook and the runtime use.

| Graph | File | Generates (in `<gen_code>`) | Consumed by |
|---|---|---|---|
| Material | `Glow.material.nmgraph` | `.mtl.glsl` (a material function) and `.material` (its description) | `RenderComponent::Materials[0] = "Materials/Glow.material.nmgraph"`, cooked from the stored code (below) |
| Script | `Mover.script.nmgraph` | `.lua`, a class table | a prefab's script (`PrefabAsset::SetScriptPath("Scripts/Mover.script.nmgraph")`, `<Script Path>` in the `.nmprefab`): each instance runs the stored Lua |
| UI | `PauseMenu.ui.nmgraph` | `.lua`, a class table | a UI document's logic (its `Graph` setting): each open document instances the stored Lua (UI/README.md, "UI graphs") |

Written for this repository. **Editor targets only**, and Qt-free: the editor
draws graphs (`Modules/Editor/Source/Private/Editor/Graph/`), but loading,
saving and compiling happen here. That lets Build > Cook Content and the
tests regenerate every graph without opening a window.

## Position in the tree

```
NimbleEditor --> NodeGraph --> GameCore --> EngineCore
                            \-> PugiXml (PRIVATE, GameCore's vendored copy)
```

**STATIC.** Unlike GameCore it owns no process-wide registry that two images
could each get a copy of. The schemas are built on first use, from GameCore's
registries, by whichever executable links this: the editor or the test.
`RefreshSchemas()` builds them again (below, "Game declarations").

## Pieces

| File | Role |
|---|---|
| `Graph.h` | The data: nodes (GUID, type name, position, literals, properties), links (`<guid>.<pin>` to `<guid>.<pin>`), variables, comments |
| `Schema.h` | What the names mean: pin types and conversions, node definitions, wildcard resolution, one compiler per schema. `GetSchemas()` |
| `GraphFile.h` | `.nmgraph` read and write (`<gen_code>` included), the path rules, the clipboard fragment, `StoreGeneratedCode`, `GenerateGraphOutput` |
| `GraphCompiler.h` | `ValidateGraph` (what every schema shares), then `CompileGraph` into the schema's compiler; diagnostics name their node |
| `MaterialSchema.cpp` | Material to GLSL: data flow from Pixel Output (and each Discard) back, one `tN` temporary per computed value, Branch and For Loop as real `if` and `for` blocks, parameters in one `mat4` at binding 2 |
| `ScriptSchema.cpp` | Script to Lua: exec flow from event nodes, pure values re-evaluated per statement; component nodes generated from the script bindings |
| `PostProcessSchema.cpp` | A post process stack (`*.pp.nmgraph`) to `.ppstack` text: one line per effect node, in the renderer's order |
| `Scripts/cook_material_graphs.py` | Cooks material graphs from their `<gen_code>` (or loose material functions) -- `-check` with glslc, loose or into a shader cache -- through GDI's own `cook_shaders.py`. Also cooks the engine's `Content/Shaders` |
| `Tools/NodeGraphGenerate.cpp` | Regenerates graphs' `<gen_code>` from the command line, as the editor does on save |

## The `.nmgraph` format

XML written with pugixml, the same choice as the text world package. There is
one file per graph, and the schema is named twice: once by the compound
extension, which is what tools route on, and once by the root's `Schema`
attribute, which is a check. A mismatch is a load error. A bare `*.nmgraph`
falls back to the attribute, with a warning.

```xml
<?xml version="1.0" encoding="UTF-8"?>
<NodeGraph Version="1" Schema="Script">
  <Properties>
    <Property Name="TickPhase" Value="PostPhysics" />
  </Properties>
  <Variables>
    <Variable Name="Speed" Type="number" Default="60" />
  </Variables>
  <Nodes>
    <Node Id="6e6f...000a" Type="Event.OnTick" Version="1" X="-400" Y="80" />
    <Node Id="6e6f...000b" Type="Variable.Get" Version="1" X="-400" Y="200">
      <Prop Name="Variable" Value="Speed" />
    </Node>
    <Node Id="6e6f...000c" Type="Math.Multiply" Version="1" X="-200" Y="160" Wildcard="number">
      <Const Pin="B" Value="2" />
    </Node>
  </Nodes>
  <Links>
    <Link From="6e6f...000b.Value" To="6e6f...000c.A" />
  </Links>
  <Comments>
    <Comment X="-420" Y="40" Width="820" Height="260" Text="Slide along +x" />
  </Comments>
  <gen_code>
    <Output Extension=".lua"><![CDATA[-- Generated by NimbleEditor from the script graph "Mover". Do not edit.
return { ... }
]]></Output>
  </gen_code>
</NodeGraph>
```

`Tests/Data/Mover.script.nmgraph` is a complete example; `Games/Sandbox/Content/Materials/Ripples.material.nmgraph` is a material with a For Loop.

- **Deterministic.** Nodes are sorted by GUID and links by their ends, and
  attributes come in a fixed order. Numbers use the shortest round-trip form
  (`std::to_chars`). An unchanged graph saves to the same bytes, and the save
  leaves such a file untouched.
- **GUIDs, never indices.** Node ids are `GameCore::EntityGuid`s: 128 random
  bits as 32 hex digits. Pins are named, so adding a pin to a node type breaks
  no link.
- **Only what differs.** A literal equal to its pin's default is not stored,
  so a changed default reaches old graphs.
- **Unknown node types survive.** A node whose type the schema no longer has,
  such as a component binding that was removed, loads as a *placeholder*. Its
  element is kept verbatim and written back unchanged, with its links. It
  fails compilation until it is deleted or the type returns.
- **Safe saves.** The file is written to `<file>.tmp` and then renamed over,
  as `SaveWorldPackage` does.
- **Clipboard.** Copy writes the selection as a `<NodeGraphFragment>`. Paste
  gives each node a fresh GUID and remaps the copied links onto the copies.
- **Generated code, last.** `<gen_code>` holds one `<Output>` per generated
  file, named by its extension (`.lua`; `.mtl.glsl` and `.material`), as
  CDATA (a `]]>` in the code is split across two sections). It is the last
  clean compile: saving a graph with errors keeps the code it had, and a
  graph that was never saved clean has none -- a cook or script load then
  fails, asking for a save. `Graph::GenCode` holds it in memory;
  `StoreGeneratedCode` fills it from a `CompileResult`. Being by extension,
  it survives renaming the file. GameCore reads a script graph's `.lua`
  without an XML library (a game build has none), so the element is written
  only in this form.

## Pin types and settings

A pin's type is one of three things. `Schema::ResolvePinType` is the one place
that turns any of them into a concrete type:

- **fixed**: `vec3`;
- **wildcard** (`*`): resolved from links, below;
- **derived** (`?`): computed by the schema from the node's settings, as the
  Component Mask's output is.

Node settings are properties of kind String, Identifier, Choice, Variable,
**Bool** or **Texture**. A Bool is a checkbox in the editor, stored as
`true`/`false`, and anything else is a validation error. A Texture is a texture
asset's runtime-relative path (`Content/Textures/Brick.nmtexture`), typed,
browsed for or dropped from the Content Browser. A render target
(`.nmrt2d`, `.nmrt3d`, or a runtime `transient://` name) is accepted too, and
samples as a texture. Anything else is a validation error.

An input pin with `Implicit` set has no constant: unlinked, the schema
supplies what it names -- a Texture Sample's UV is "Texture Coordinate". The
node and the Details panel show those words instead of a value.

## Wildcards

Math nodes are `*`-typed: a material Add is float, vec2, vec3 or vec4, and a
script Add is number or Vector3. A node's type is, in order:

1. its stored `Wildcard`;
2. otherwise inferred from its input links. If they disagree, the widest
   wins: `WildcardTypes` is ordered narrowest first. The rule looks at output
   links only when no input decides;
3. otherwise the first allowed type.

The inference never depends on the order links happen to be stored in, so a
graph generates the same code in memory and after a save and reload (a test
checks this). The editor stores a type when a link first fixes it, and
Details > Type overrides it.

## Script graphs

- Event nodes each become one function of the class table: On Start, On
  Tick, On Destroy, On Event, and On Overlap Begin / On Overlap End. The
  overlap events become `OnOverlapBegin(self, other, mine)` /
  `OnOverlapEnd(self, other, mine)`, which GameCore's overlap pass calls; their
  outputs are Other and Mine (which of the instance's entities was touched).
- A statement's **Then** leads to the next statement.
- Pure nodes are evaluated where a statement needs them, into `local tN`,
  once per statement. So a Get after a Set sees the new value.
- A statement's own outputs (a Raycast's Hit) are locals declared at the top
  of its function. They can be read only in that function.
- Values travel as **lanes**, as the bindings pass them. A Vector3 is three
  numbers, a Color four, a Box six. Vector math is written per component and
  allocates nothing.
- Variables are fields of the class table (`Speed = 60,`), written per
  instance through `self`.
- On Event subscribes in `OnStart` and unsubscribes in `OnDestroy`, so a
  destroyed instance's handler never runs.

**Components come from their bindings.** Every type registered with
`GAMECORE_DEFINE_COMPONENT_SCRIPT` gets these nodes:

- Get, Has, Add and Remove on an entity;
- a getter per field, plus a setter unless the field is read-only;
- a call per method.

A method's pins come from the optional signature on its binding:

```cpp
Bind.Method("Translate", [](TransformComponent& C, ScriptCall& Call) { ... }, "Delta:Vector3");
Bind.Method("Scaled",    ...,                                                  "Factor:number -> Result:number");
```

The types are `number`, `integer`, `bool`, `string`, `Vector3`, `Color` and
`Entity`. A method without a signature still gets a node, called with no
arguments, and a compile warning.

**Script libraries come from theirs too** (`GameCore/ScriptLibrary.h`). Each
library is a palette category, and its members become nodes typed
`Library.<Library>.<Member>`:

| Member | Nodes | Generated |
|---|---|---|
| `Function` | a statement | `Total1 = Sandbox.AddScore(t1)` |
| `Pure` | a value node | `local t2 = Sandbox.RankForScore(t1)` |
| `Variable` | Get, and Set unless `ReadOnly` | `Sandbox.GetScore()`, `Sandbox.SetScore(t1)` |
| `Event` | On *Name* (an event node), Emit *Name* | `Events.On("ScoreChanged", ...)`, `Events.Emit("ScoreChanged", t1)` |

A typed On *Name* is On Event with its name fixed and its outputs named and
typed. An `integer` argument is floored, since the bus carries numbers. Emit
*Name* passes every argument, linked or not. An event whose parameters do not
fit the bus (more than four, or a Vector3) gets no nodes and a log warning.

**Script structs are pin types** (`GameCore/ScriptStruct.h`). Each registered
struct becomes a type named after it. It also gets **Make *Struct*** and
**Break *Struct*** nodes under Structs, and can be a graph variable's type.
Its value travels as one lane per field, named after the fields (`Stats_Value`,
`Stats_ID`, and `Where_X` for a Vector3 field). An unlinked struct input is all
zeros, not the C++ defaults: build one with Make. The lane layouts are kept
across `RefreshSchemas()`, so a graph that was already open still compiles.

### Game declarations

A game module declares components and libraries in its own image
(`Games/Sandbox/Source/Private/Sandbox/SandboxScripting.cpp`), so they exist only while it is
loaded. The editor loads it briefly to read them
(`EditorGraphs::RefreshGameDeclarations`):

- at startup, before any graph opens;
- after Build > Compile Source succeeds, or when a Play that kept the old
  module stops;
- on Build > Refresh Script Nodes.

`RefreshSchemas()` copies what is registered, so the nodes outlast the
module. Schemas built earlier are retired, not freed: a graph already open
keeps working with the nodes it had until it is reopened. A graph using a
game's nodes that is opened without the game loads them as placeholders and
keeps them.

`Games/Sandbox/Scripts/Pickup.script.nmgraph` (the game's component, library
functions and variables, a typed Emit) and `ScoreBoard.script.nmgraph` (typed
On nodes) are the examples.

### UI graphs

The UI schema is the script schema in another flavour (`ScriptSchema.cpp`,
`EScriptFlavour::UI`). It has the same nodes, without those that need an
entity: On Start, On Destroy, the phase and overlap events, Self, and the
prefab nodes. In their place it adds:

- **On Document Open** and **On Document Close.** On Event handlers listen
  between these two.
- **UI Event**, a handler a document's `Graph:<Handler>` action calls. It
  outputs `Value` (a bool when `ValueType` is Bool) and `Sender`.
- **This Document** (`self.Document`), **Close This Document**, and widget
  statements whose `Widget` setting (`EPropertyKind::WidgetName`) the editor
  offers from the linked document. Their templates use `{@Property}`: the
  node's setting as a Lua string.

The generated table is `{ variables, OnOpen, OnClose, OnTick, <Handler>,
Event_<X> }`; there is no `TickPhase`. Handler names must be unique Lua
identifiers that the table does not already use. The graph's `Document`
property names the `.nmui` it serves, which the editor uses. The runtime link
is the document's `Graph` setting. `Tests/Data/UIMenu.lua` is the golden
output.

## Material graphs

A material graph `Materials/Glow.material.nmgraph` generates two outputs,
both stored in its `<gen_code>` (RenderCore's MATERIALS.md has the whole
design):

- **`.mtl.glsl`**, a *material function*, not a whole shader: the
  material's uniform block and `CalcMaterial(Inputs, Surface)` -- plus
  `CalcMaterialOffset(Inputs)` when World Position Offset is linked. The
  engine's templates (`Engine/Content/Shaders/MaterialTemplate_VS/PS.glsl`)
  own `main()` and include it as `<Material.glsl>`, once per permutation.
- **`.material`**, what the renderer needs to draw it:

  ```
  NimbleMaterial 3
  Domain Opaque
  Shading Lit
  TwoSided 0
  ClipValue 0.5
  MaxOffset 0
  HasOffset 0
  BlockSize 176
  Param Color vec3 160 0.2 0.8 1 0
  Texture 1 Nearest Default Content/Textures/Brick.nmtexture
  ```

**Material Output.** Its pins are the surface -- BaseColor, Metallic,
Roughness, Specular, Emissive, Opacity, OpacityMask, Normal,
AmbientOcclusion -- and World Position Offset; its settings are Domain
(Opaque, Masked, Translucent, PostProcess), Shading (Lit, Unlit), Two Sided,
Clip Value and Max Offset. Only a linked pin, or one set to something other
than its default, is written; the rest keep `DefaultMaterialSurface`'s value.
A pin the domain or shading never reads (BaseColor on an Unlit material) is a
warning. The first output, **Pixel Output** (one colour), still compiles: as
Unlit and Translucent, how every material drew before.

**Parameters** are members of one std140 block at binding 2, in name order,
after the engine's 160 bytes (the tint, Clip Value, Two Sided, and the draw's
baked lighting: RenderCore's MaterialDescription.h). The offsets are
computed here and written to the `.material`, and the renderer fills the block
byte for byte (GDI's `GDISetUniformBlock`). Any number fit, up to the block's
1024 bytes.

**Textures** are two nodes. A **Texture Object** names a texture asset and how
it is sampled: its settings are the Texture and the sampler, **Filter**
(Default, Nearest, Linear) and **Wrap** (Default, Repeat, Clamp, Mirror);
Default keeps what the texture was imported with. Its **Texture** output is of
the type `texture` -- a sampler, not a value: no constant, no conversions --
and its **Size** output is the texture's width and height in texels (one texel
is `1 / Size` in UV). A **Texture Sample** reads the Texture Object linked into
its **Texture** at its **UV** (unlinked: the texture coordinate) and gives RGBA,
RGB, R, G, B and A. One Texture Object feeds any number of samples, each at its
own UV -- a blur, a detail layer, a flipbook.

Each distinct texture-and-sampler combination is one material texture slot,
from 1 (slot 0 is a PostProcess material's scene), declared
`Material_Texture<slot>` at binding 4 + slot; seven fit. Texture Objects take
slots in GUID order, used or not, and two naming the same texture and sampler
share one. The `.material`'s `Texture` lines say which file and settings fill
each slot. One sample node's outputs share one sample. Both stages sample. In
the pixel stage, a texture with a baked mip chain is read trilinearly with a
Linear filter. In World Position Offset a sample reads the full-size level
(`textureLod`), as the vertex stage has no derivatives. A Texture Object with no texture, or a Texture
Sample with no Texture Object linked, is an error.

**Normal Map** (category Textures, pixel stage only) turns a tangent-space
normal map's colour into a world-space normal, for Material Output's Normal.

- **Inputs:** Color is the map's colour, usually a Texture Sample's RGB;
  unlinked it is flat. Strength scales the tilt. UV must be the UV the map was
  sampled at; unlinked it is the texture coordinate.
- **Format:** OpenGL means green points up the image (Blender, Substance's
  OpenGL export); DirectX means it points down (Unreal, 3ds Max).
- **The tangent frame:** the mesh's own MikkTSpace tangent (`MeshData::Tangents`,
  the frame normal maps are baked against) where it has one and UV follows
  the texture coordinate -- itself, or scaled and offset (tiled), not turned
  or mirrored. Otherwise it is built per pixel from how the world position
  and UV change across it (`Material_NormalMap`, MaterialCommon.glsl, a
  cotangent frame), constant across a triangle. That one is signed by the
  screen's handedness, so every backend and back faces agree.
- **Import the map linear:** the importer does so for a name that says normal
  (see the Editor's README).
- **Verified on Vulkan:** a map tilted right and up the image tilts the normal
  right and up on screen.

**Reflect** (category Textures, pixel stage only) samples a render target that
a Scene Capture Probe fills, for environment reflections. Its **Target**
setting names the target, which takes a texture slot like a Texture Object
does. What it samples depends on the target's kind:

- **`.nmrt2d`, a planar mirror:** the target is read at the pixel's screen
  position flipped in X (`Material_MirrorUV`). **Distortion** (vec2), if
  linked, is added to that UV, for ripples.
- **`.nmrt3d`, a cube:** the target is read along the view vector reflected
  in **Normal** (vec3; unlinked, the vertex normal), through
  `Material_SampleCubeStrip`.

The node gives **RGBA** and **RGB**. A Target that is empty, or is not a
render target, is an error. For a mirror or chrome look, the usual graph sends
Reflect.RGB times a tint into Emissive, over a dark Base Color with low
Roughness. LightLab's `Mirror` and `Chrome` materials are built this way.

**Upgrading.** A schema can rewrite a graph an older editor saved as it is read
(`Schema::UpgradeGraph`, for files and pasted fragments). Texture Sample
version 1 named its texture itself; read now, each gains a Texture Object --
one per distinct texture and sampler, shared by the samples that named them,
with an id derived from the first one's so the slots stay put -- and the
reader warns that the graph was upgraded. Saving writes the new form.

**Two stages.** World Position Offset is the vertex stage's root; everything
else is the pixel stage's. Each stage is compiled from its own roots, so a
node both reach is written in both functions. A node's `StageMask` says where
it can run: Pixel Coordinate, Pixel Depth, Clip Position, Scene Texture and Scene Depth are
pixel-only. A pixel-only node feeding World Position Offset, however
indirectly, is a compile error on that node; the editor refuses the link
(`Schema::CanLinkStages`), greys such nodes in the palette when dragging from
a vertex path, and badges them "Pixel".

**Selecting components.** There are two nodes for picking out parts of a vector:

- **Component Mask** has R, G, B and A checkboxes and passes the ticked
  components through in that order. R and B of a vec3 is `.xz`, a vec2.
- **Swizzle** takes 1 to 4 letters, `xyzw` or `rgba`, in any case, but not
  mixed. It reorders and repeats: `zyx` reverses a vec3; `xxx` of a float
  becomes `vec3(f)`.

Either node's output type follows its settings, not its links. The pin is
declared `DERIVED_TYPE`, and `MaterialSchema::ResolvePinType` computes it.
Every type question in the compilers, the validation and the editor goes
through that one hook, so a downstream wildcard node follows along: an Add fed
a vec2 mask becomes vec2.

A component the input does not have (B of a vec2, `z` of a vec2) is an error on
the node, never a silent clamp. `DescribeNode` gives the editor the node's
header text, `.xz → vec2`.

**Control flow.** The Logic nodes write real statements:

- **Branch** compares A with B (`>`, `>=`, `<`, `<=`, `==`, `!=`) and gives
  True or False. It is an `if` block. With **Ternary** ticked in Details it is
  one expression instead, `A > B ? True : False`: both sides are computed
  first, and a Hint does not apply (it is a warning).
- **For Loop** and **For Loop End** are a pair, joined by their Loop pins, and
  everything between them is the body of a `for`. Value starts as Initial and
  becomes Next each time round. Index counts 0, 1, 2 and so on. Result is the
  value after the last time round. Count is a constant unless something is
  linked to it.

Each value is computed in the innermost block that all of its uses share. A
value only the True side needs is computed inside that side, so it is skipped
when False runs. A value both sides need is computed once, before the `if`.
Index and Value exist only in the body. Reading them anywhere else is an error
on the reading node, as is a For Loop without exactly one For Loop End. The
For Loop End takes its For Loop's type. Unless Details sets that type, it is
the widest suggested by the links of either node.

**Discard.** A Discard node throws the pixel away when A compares with B as
its Compare says. The default is `<` and B is 0.5, so it discards when an alpha
is below 0.5. Like Pixel Output it is a root, so it needs no link out, and a
graph may have any number of them. Each becomes `if(A < B) { discard; }` at the
top of `main`, in GUID order, before the colour. A value that a Discard and the
colour share is computed once, above both.

**Hints.** Branch has a Hint of None, Branch or Flatten; For Loop has None, Loop
or Unroll. Unroll needs a constant Count. A hint becomes a `HINT_*` macro from
`Engine/Content/Shaders/MaterialPlatform.glsl`. A shader includes that header first, and only
when it uses a hint. The header maps each hint per platform:

| Platform | `HINT_BRANCH` becomes |
|---|---|
| Vulkan (glslc) | `[[branch]]`, under `GL_EXT_control_flow_attributes`, into the SPIR-V |
| D3D12 | `[branch]`, written by spirv-cross from that SPIR-V |
| OpenGL | `/* branch */`, a no-op: drivers do not take the attributes |

The macros are comments rather than empty because `cook_shaders.py`'s
preprocessor substitutes only defines that have a value.
`cook_material_graphs.py` resolves every `#include` against
`Engine/Content/Shaders`.

The inputs read `MaterialInputs`, which each stage's template fills:

- Texture Coordinate, Vertex Color, Vertex Normal and World Position (both
  stages; World Position is before the offset in the vertex stage);
- Clip Position, Pixel Coordinate and Pixel Depth (linear and device; pixel only);
- Viewport Size, Mouse, Instance Tint and Time (both);
- Scene Texture and Scene Depth (PostProcess materials only; Scene Depth gives the
  stored depth and the distance from the camera, from the scene depth in slot 7,
  so a PostProcess material samples at most 6 textures of its own);
- Texture Object and Texture Sample (both; Textures in the palette).

**Drawing one.** A primitive names the material by its graph's runtime path:
a slot of `RenderComponent::Materials`, `"Materials/Glow.material.nmgraph"`
-- slot *i* for mesh section *i*, slot 0 for a quad. (A bare `"Glow"`, as
worlds saved before, still means that graph; they are upgraded on load.) The
cook reads the graph's `<gen_code>` and writes, named by the path without its
extension, `Materials/Glow.material` and the permutations its domain and
shading need, `Materials/Glow@<key>` under `Shaders/Cooked/<Platform>/`; that
is what RenderCore loads. NimbleCook (`Engine/Tools/NimbleCook`; the editor's
Build > Cook Content runs it) cooks a game's graphs into its module's shader
cache, mounted when the module loads, and the build stages it with
`nimble_stage_materials` (`Engine/cmake/NimbleMaterials.cmake`); Editor
targets also stage them loose. The
editor cooks one for its viewport on save and, with Live Preview, on every
clean recompile. The graph window's **Preview** dock then shows it, drawn by
that same renderer.

GDI is a vendored subtree and is never edited from here. So
`Scripts/cook_material_graphs.py` **imports** its `cook_shaders.py` read-only
and reuses its preprocessor and tool lookup. `#include <Common.glsl>` resolves
against `Engine/Content/Shaders`, which holds the engine's own shaders (Basic,
Mesh, Screen and their includes). NimbleCook cooks that folder the same way,
and the engine's build stages it into the runtime directory; GDI's own cook (and its `.qrc` bundles,
which only a Qt host needs) is switched off with `GDI_COOK_SHADERS`.

```
python Scripts/cook_material_graphs.py -check Games/Sandbox/Content/Materials/Glow.material.nmgraph
python Scripts/cook_material_graphs.py -target Vulkan -src Games/Sandbox/Content/Materials -root Games/Sandbox -out <runtime>/Shaders/Cooked -data-out <runtime>
python Scripts/cook_material_graphs.py -target Vulkan -src Games/Sandbox/Content/Materials -root Games/Sandbox -cache <runtime>/Shaders/Cache/SandboxGame.Vulkan.nmsc -module SandboxGame
```

`-src` takes a file or a folder; `-root` is what graphs' runtime paths are
relative to (the game's folder); `-data-out` is where loose descriptions go;
`-defaults` adds the shared MaterialDefault vertex shaders (below
`-subdir`). Loose `.mtl.glsl` files, each with its `.material` beside it,
still cook below `-subdir` -- the editor's live cook of an unsaved graph.
`NodeGraphGenerate [-module <game module>] <graph.nmgraph>...` regenerates
graphs' `<gen_code>` from the command line, as the editor does on save.
`-module SandboxGame.dll` loads a game module first, so that graphs using
its components, libraries and structs compile. Run it from the game's
binaries folder so the module's dependencies resolve.

## Post process stacks

A `*.pp.nmgraph` is a **post process stack**: the effects a Post Process volume
applies, and their settings (RenderCore's `RENDERPIPELINE.md`, "Post process").

- **Nodes:** each node is one effect, with properties and no pins. Ambient
  Occlusion, Depth of Field, Motion Blur, Bloom and Antialiasing appear at most
  once each;
  Material (a PostProcess material graph, run Before or After Effects, by Order)
  may appear any number of times.
- **Order:** where a node sits on the canvas means nothing, because the
  renderer runs the effects in a fixed order. Ambient Occlusion runs before the
  lighting, not in the post chain, so it darkens only ambient light. A stack without a node leaves
  that effect alone, so a smaller volume can add Depth of Field without
  touching the glow a wider one sets.
- **Checks:** numbers are typed as text and checked against each setting's
  range when compiled.
- **Output:** the compiled output, `.ppstack`, is one line per effect, then one
  per material, with the path last:

```
# Post process stack Arch
Effect DepthOfField FocusDistance=350 FocusRange=250 MaxBlur=10 NearBlur=false
Effect Bloom Threshold=0.8 Intensity=0.9 Radius=0.75 Levels=5 Tint=1,0.85,0.7
Material Stage=After Order=0 Path=Content/Materials/Negative.material.nmgraph
```

- **Staging:** the graph file itself is staged beside the executable, where the
  runtime reads its `<gen_code>` (GameCore's `GraphText.h`) -- as a script graph
  is read, so a game build needs no NodeGraph. Content Browser right-click >
  New PostProcess Graph... starts one, with Bloom and Antialiasing, in the
  browser's folder.

## Tests

`NodeGraphTests` (ctest `NodeGraph.Tests`, on by default with
`NODEGRAPH_BUILD_TESTS`) covers:

- the path rules;
- byte-identical save, load and save, `<gen_code>` included (a `]]>` in it too);
- placeholders;
- paste remapping;
- validation errors landing on the right node;
- golden generated code in `Tests/Data/`;
- a **run** of the generated Lua: an instance of a prefab whose script is
  Mover moves 60 units in a second -- as a `.lua`, and as a `.script.nmgraph`
  running its `<gen_code>`;
- a script library declared in the test (`TestLib`): its nodes, golden
  `Scorer.lua`, a run through its functions, variable and typed event,
  `RefreshSchemas` picking up a late library, and component bindings and
  libraries unregistered and registered again, as a reloaded module's are;
- a script struct (`TestStats`): its pin type and Make/Break nodes, golden
  `Stats.lua`, a run through a component field, a variable and Native
  functions, and an unregister and re-register.

`NodeGraph.MaterialGLSL` compiles every permutation of the golden material
functions with glslc when Python and the Vulkan SDK are present.

A missing golden file is written and fails once, so a new one is always looked
at. After an intended change to the output, run with
`NODEGRAPH_UPDATE_GOLDEN=1` and review the diff.
